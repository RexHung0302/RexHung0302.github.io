[DevOps Note] — GitLab CI/CD：推送 Tag 後自動驗證，再手動部署到 VM

發表於 2026-08-13 分類於 Code ， Note ， DevOps
文章字數： 15k 所需閱讀時間 ≈ 14 分鐘

Introduction & 前言

以前 Side Project 要上線時，筆者都是先 SSH 進 VM，再手動執行 git pull、docker build、Migration 與重啟服務。流程不難，但每次都要重新確認指令，久了不只麻煩，也很容易漏掉測試、打錯版本，甚至在錯誤的目錄執行部署。

所以這次把流程搬進 GitLab CI/CD：本機只負責建立並推送版本 Tag，GitLab 收到 Tag 後自動執行檢查；全部通過後，Pipeline 會留下一個需要人工點擊的 Production Deploy Job。按下部署，GitLab Runner 才會使用專用 SSH Key 連進 VM，由 VM 自己取得指定 Tag、建置 Docker Image、執行 Migration 並重啟服務。

這種做法沒有追求「一 Push 就直接上正式環境」，而是刻意保留最後一道人工確認。對個人專案或小型服務來說，既省掉重複操作，也避免每次建立 Tag 就立刻動到正式機。

本文所有專案名稱、Domain、帳號、IP 與路徑都是示意值，請依自己的環境替換；不要直接照抄 deploy.example.com 或 /opt/example-app。

架構與安全邊界

這個版本選擇在 VM Build，而不是在 GitLab Runner Build 完再把 Image 傳到 VM。原因很單純：第一版需要的基礎設施比較少，不必先處理 Container Registry、Image Pull 權限與 Registry 清理策略。

各層負責的事情如下：

位置 負責內容 不應該放的東西
本機 開發、更新版號、建立與 Push Tag 正式機自動部署權限
GitLab Runner 驗證程式、顯示手動部署按鈕、透過 SSH 下達部署命令 正式站 .env.production 全文
VM 保存正式環境變數、Build Image、Migration、啟動服務 個人日常使用的 SSH Private Key
GitLab CI/CD Variables VM Host、部署帳號、CI 專用 SSH Private Key、Known Hosts 提交進 Repository 的明文 Secret

最重要的原則有三個：

  1. 部署固定 Tag，不直接部署 VM 當下碰巧存在的 Branch。
  2. 正式機使用專用部署帳號，不讓 CI 直接使用 root。
  3. Private Key 只存在本機安全位置與 GitLab Variable；VM 只放 Public Key。

事前準備

開始前需要：

  • 一個已啟用 GitLab CI/CD 的 Repository
  • 一台可以透過 SSH 登入的 Linux VM 或 VPS
  • VM 已安裝 Git、Docker、Docker Compose Plugin 與 curl
  • 專案根目錄已有可用的 Dockerfile 與 Production Compose 檔
  • 正式環境變數已安全放在 VM，例如 /opt/example-app/.env.production
  • GitLab Runner 可以使用 Docker Executor 執行 Job

本文範例統一使用：

尖括號通常代表「請替換內容」。在 zsh 直接輸入 ssh root@<PRODUCTION_HOST>，Shell 會把 < 當成重新導向符號，最後出現 no such file or directory。實際執行時請寫真正的 Domain 或 IP，而且不要保留尖括號。

SSH 不只要驗證「Client 有沒有正確 Private Key」，Client 也要確認「連到的是不是真的那台 VM」。這就是 known_hosts 的用途。

不要在 CI Job 執行時才動態 ssh-keyscan 並立刻信任結果。 如果當下 DNS 或網路被劫持，Runner 可能把攻擊者的 Host Key 當成正確答案。GitLab 官方也建議預先取得並保存 Host Key；Host Key 未預期改變時，部署應該直接失敗，讓人先確認 VM 是否重建或遭到中間人攻擊。

避免同時部署 Production

同一個 Resource Group 同時間只允許一個 Job 使用，避免兩個 Tag Pipeline 一起對同一台 VM Build、Migration 與 Restart。

為什麼用 git show 取出部署腳本

如果直接在 VM 執行目前 Working Tree 的 scripts/deploy-production.sh，那支 Script 可能還是上一版。CI 先從指定 Tag 取出 Script 到 /tmp，確保「部署 v1.2.3」時，連部署邏輯也是 v1.2.3 版本。

Protected Variable 在 Job 裡是空的

最常見原因是 Tag 沒有被保護。Variables 勾選 Protect 後，請同步建立 v* Protected Tag Rule。

SSH_PRIVATE_KEY 出現 error in libcrypto

確認：

  • Variable Type 是 File
  • 貼入完整 OpenSSH Private Key
  • END OPENSSH PRIVATE KEY 後有一個換行
  • 沒有把 Public Key 貼進 Private Key Variable

.env.production 要不要放進 GitLab

如果 Build 與 Runtime 都發生在 VM，正式 .env.production 留在 VM 即可，不需要整份複製到 GitLab。CI Variables 只保存「GitLab 如何連到 VM」所需的值。

另外要注意前端 Framework 的 Public Environment Variable 通常會在 Build 時寫進 Bundle。即使 VM Runtime 已經更新 .env.production，只要值需要進 Browser Bundle，就仍然必須重新 Build。

Docker Database 顯示 unhealthy

先不要一直重跑整個部署，依序查看：

如果 Database Log 顯示 Crash Recovery 後已經 ready to accept connections，Health Check 也回到成功，有可能只是 Deployment 等待時間太短；反之若 Volume、帳密或 Migration 出錯，就要先修復根因。

VM Build 很慢

第一版在 VM Build 的優點是簡單，缺點就是每次部署都要在正式機建置。可以先改善：

  • Dockerfile 先 Copy Lock File 並安裝依賴，再 Copy Source，增加 Layer Cache 命中率
  • 不要在部署前執行 docker builder prune -a
  • npm、pnpm 與 Docker BuildKit 使用 Cache Mount
  • 避免每次覆蓋整個 Repository 或 .env.production

後續再升級成 GitLab Runner Build Image、Push GitLab Container Registry，VM 只負責 Pull 與 Restart，部署時間會更穩定。

Rollback 與後續優化

最低限度的 Rollback 是重新部署上一個已知正常 Tag：

但 Database Migration 不一定能跟著倒退。要讓 Rollback 可靠，需要：

  • Migration 採 Backward-compatible 設計
  • Migration 前自動備份 Database
  • Build 新 Image 前替舊 Image 加上 Rollback Tag
  • 健康檢查失敗時不要刪除舊 Image
  • 將部署與資料轉換拆成不同步驟

後續可以依序升級：

  1. GitLab Container Registry：CI Build 並 Push Image，VM 只 Pull
  2. Dependency Proxy / Build Cache：減少重複下載
  3. Protected Environment：限制誰能點 Production Deploy
  4. Deployment Approval：正式環境需要指定角色核准
  5. Staging Environment：同一個 Tag 先部署 Staging，再升 Production
  6. Observability：部署後自動檢查 Log、Sentry、Metrics 與 Smoke Test

總結

完成後，日常發布只需要：

接著等待 GitLab 自動驗證，最後到 Pipeline 點一下 Deploy。VM 上的 Git、Docker Build、Migration、Restart 與健康檢查都由版本化 Script 統一執行。

這套流程看起來比直接 SSH 上去多了不少設定，但它真正解決的不是「少打幾行指令」，而是讓每一次正式部署都有固定版本、固定步驟、檢查結果與可追蹤紀錄。等第一版穩定後，再把 Build 搬到 CI 與 Container Registry，就能逐步從手動部署走向更完整的 Release Pipeline。
