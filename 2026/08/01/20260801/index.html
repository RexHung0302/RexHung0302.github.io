[Security Note] — 前端驗證碼真的安全嗎？用 Cloudflare Turnstile 建立前後端人機驗證

發表於 2026-08-01 分類於 Code ， Note ， Cloudflare
文章字數： 15k 所需閱讀時間 ≈ 14 分鐘

Introduction & 前言

相信很多人都看過這種驗證碼：一張扭曲的英數字圖片，旁邊再放一顆重新整理按鈕，使用者必須猜出上面到底寫了什麼。

筆者的 Side Project 很久以前也自己刻了一套，直到最近回頭檢查才發現，這個驗證碼與其說是在防機器人，不如說只是在考驗正常使用者的視力（笑

更嚴重的是，答案存在前端、比對也發生在前端，後端 API 完全不知道有人機驗證這件事情。攻擊者根本不需要辨識圖片，只要直接呼叫 API 就能無視整套流程。

所以這次決定把舊文字驗證碼移除，改用 Cloudflare Turnstile，並且在 Express 後端呼叫 Siteverify API 驗證 Token。

這次實際改造的專案使用 Vue 2，所以文章會以 Vue Component 作為主要範例；不過 Turnstile 本身並不綁定前端框架，後面也會補上一份 React Hooks 的對應實作。無論是 Vue、React 或原生 JavaScript，真正不能省略的都是後端 Siteverify。

這篇最重要的觀念只有一句：換掉前端 Widget 不是重點，把是否放行的決定權移到後端才是。

Summary & 摘要

本文實際案例使用的主要技術：

  • Vue 2.7、Vue CLI、Webpack、Pug、BootstrapVue
  • Vuex、vee-validate
  • Express、Sequelize、Joi、Axios
  • Cloudflare Turnstile

Vue 2 是本篇的實戰案例，不是使用 Turnstile 的必要條件；React、Vue 3、Next.js 或其他能載入 Browser SDK 並將 Token 送往後端的前端技術都能使用同一套安全流程。

這不是驗證碼長得不夠複雜，而是信任邊界擺錯地方。瀏覽器裡的 JavaScript、欄位與判斷都能被使用者修改，不能拿來當最後的安全決策。

Turnstile 的安全驗證流程

Cloudflare Turnstile 可以獨立使用，不要求網站 DNS 一定要託管在 Cloudflare，也不必開啟橘色雲朵。它真正完整的流程分成前端與後端兩段。

整體流程如下：

  1. Vue 頁面使用公開的 Site Key Render Turnstile Widget
  2. 使用者通過 Challenge 後，Cloudflare 簽發一次性 Token
  3. 前端把表單資料與 Token 一起送到 Express API
  4. Express Middleware 使用私密的 Secret Key 呼叫 Siteverify
  5. Cloudflare 回傳 success: true 才執行 Controller
  6. 驗證失敗就拒絕 Request，前端 Reset Widget 並取得新 Token

前後端職責可以這樣看：

層級 負責內容 是否能當最終依據
Vue Widget 顯示 Challenge、取得 Token、改善 UX 否，前端可以被竄改
Express Middleware 帶 Secret 呼叫 Siteverify，決定是否放行 是

Cloudflare 官方也明確說明，只有前端 Widget 並不完整，Server-side validation 是必須的。Token 最長只有 300 秒，而且每一組只能成功驗證一次。

Vue 2 前端元件實作

因為這個專案是 Vue SPA，而且有多個 Create、Edit 頁面共用驗證，所以使用 render=explicit 手動管理 Widget 的生命週期。

這裡有四個刻意做出的選擇：

設計 原因
?render=explicit SPA Route 切換或動態表單需要自己控制 Render 時機
Script 使用固定 ID 多頁共用元件時，整站只載入一次 SDK
使用 $refs.container 避免全域 ID 在多實例之間互相打架
beforeDestroy() 呼叫 remove() 避免換頁後殘留舊 Widget

Cloudflare 目前的官方文件也建議 SPA、動態內容與需要生命週期控制的頁面使用 Explicit Rendering。

本機與自動化測試

正式 Site Key 會限制允許的 Hostname，本機自訂 .local Domain 或自動化 Browser 很容易無法通過。Cloudflare 官方提供 Dummy Keys，能穩定測試成功、失敗與 Token 重複使用。

Site Key Secret Key 行為
1x00000000000000000000AA 1x0000000000000000000000000000000AA 永遠成功
2x00000000000000000000AB 2x0000000000000000000000000000000AA 永遠失敗
3x00000000000000000000FF — 強制顯示互動 Challenge
1x00000000000000000000AA 3x0000000000000000000000000000000AA 回傳 timeout-or-duplicate

Dummy Keys 能在任何 Domain 使用，很適合 Local、Cypress、Playwright 或 CI；但絕對不能放到 Production，而且測試 Site Key 必須搭配測試 Secret Key，正式 Secret 不會接受 Dummy Token。

官方測試金鑰與最新行為可以查看 Test your Turnstile implementation。

實際踩到的坑

坑 1：process.env 全部都是字串

這種 Bug 最陰險的地方是 .env 明明寫著 false，功能卻從來沒有真的關掉。

坑 2：Joi 擋掉新欄位

前端加入 cf_turnstile_token 後，如果 Joi Schema 沒有同步宣告，Request 會先被 Unknown Field 擋掉，而且錯誤訊息看起來與 Turnstile 完全無關。

坑 3：修改 Vue CLI 的 .env 後沒有重啟

Vue CLI 在 Build 階段將環境變數寫入 Bundle，HMR 不會重新讀取 .env。

Widget 一片空白通常先檢查環境變數是否載入；出現紅色錯誤框則檢查 Site Key 與 Hostname 是否授權。

坑 4：Token 失敗後沒有 Reset

原本 Promise 只有 .then()，加上 Turnstile 後，API 失敗再送一次會重用已花掉的 Token，使用者就會永遠卡在 timeout-or-duplicate。最後在 .catch() 呼叫 reset() 才補齊完整流程。

坑 5：前後端開關不同步

狀態 結果
前端開、後端關 多做一次 Widget，但 API 仍會放行
前端關、後端開 所有 Request 沒 Token，等同網站停機

因此部署順序最好固定為：

Fail-open 還是 Fail-closed

如果 Express 無法連上 Cloudflare Siteverify，到底要放行還是擋住？這題沒有所有專案都適用的答案。

策略 Cloudflare 暫時無法連線 風險
Fail-open 表單仍能送出 攻擊者可能利用驗證服務異常繞過防護
Fail-closed 表單暫時不能送出 第三方服務異常會影響可用性

這個預約表單選擇 Fail-closed：Siteverify 發生 Timeout 或其他錯誤時直接拒絕，因為寧願讓使用者稍後重試，也不希望驗證悄悄失效。

但如果是高營收的電商結帳，停機成本可能比 Bot 穿透更高，就要搭配 Rate Limit、Queue、重試策略與監控重新評估。安全與可用性往往不是是非題，而是業務風險題。

總結

原本的文字驗證碼看起來像一道門，但鑰匙與門鎖都放在使用者的 Browser 裡，攻擊者甚至可以直接繞過那扇門走 API。

Cloudflare Turnstile 真正改善的不是圖片變漂亮，而是建立了一個能由後端驗證的一次性 Token：

實作時最容易忘記的三件事情：

  1. Secret 永遠只能留在後端
  2. 每一組 Token 只能用一次，失敗後必須 Reset
  3. 前端 Widget 不能取代後端 Siteverify

把這三件事情守住，才算真的從「看起來有驗證」升級成「後端確實有驗證」。
