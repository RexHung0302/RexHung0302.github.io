[Third party service Note] — GoDaddy 網域託管到 Cloudflare，順便搞定 SSL 與 WAF

發表於 2026-07-30 更新於 2026-08-01 分類於 Code ， Note ， Cloudflare
文章字數： 11k 所需閱讀時間 ≈ 10 分鐘

Introduction & 前言

之前有幾次把網站架設到 AWS、VPS 上的經驗，但網站架好之後還有一件很容易被忽略的事情：網域到底要放在哪裡管理？

筆者的網域是在 GoDaddy 購買，原本 DNS 也直接放在 GoDaddy，這當然可以正常使用；不過如果還想順手加上 CDN、免費 SSL、DDoS 防護與 WAF，Cloudflare 會是一條相對省事的路。

這篇文章會記錄怎麼把 GoDaddy 買的網域，改由 Cloudflare 託管 DNS，最後再把 HTTPS 與 WAF 一起設定好。

先釐清一個很常見的誤會：本文不會把網域「移轉」到 Cloudflare Registrar，也不會改變續約與付款的地方。網域依舊在 GoDaddy，只是把 Nameserver 換成 Cloudflare，之後 DNS Record 要到 Cloudflare 管理。

AWS 還是 Cloudflare？

嚴格來說，這裡比較的不是「把網站架在 AWS 還是 Cloudflare」，而是把 權威 DNS（Authoritative DNS） 交給誰管理：

  • AWS 這條路通常是 Route 53 + CloudFront + ACM + AWS WAF
  • Cloudflare 則是把 DNS + CDN/Proxy + Universal SSL + 基礎 WAF 整合在同一個 Dashboard

兩邊都能做到類似的結果，但適合的情境不太一樣。

比較項目 AWS Cloudflare
上手難度 服務拆得比較細，需要理解 Route 53、CloudFront、ACM、WAF 之間的關係 功能集中在同一個網域 Dashboard，個人網站比較容易上手
DNS Route 53 功能完整，支援 Alias、Health Check、Failover、Latency 等複雜路由 DNS 操作直覺，開啟橘色雲朵就能讓 HTTP 流量經過 Proxy
SSL ACM 憑證本身通常不另外收費，但要掛到 CloudFront、ALB 等支援的 AWS 服務 完整託管後自動提供免費 Universal SSL，不用自己申請與續約
WAF 規則、Web ACL 與 AWS 資源整合彈性高，適合完整 AWS 架構 Free 方案已包含精簡版 Managed Ruleset，也能建立有限數量的 Custom Rules
費用理解 多數服務按用量計費，彈性高，但流量、請求、規則與 Log 都可能影響帳單 Free 方案就能涵蓋一般部落格常用的 DNS、CDN、SSL 與基本防護
適合情境 系統本來就在 AWS、多區域容錯、需要 IaC 或精細權限與流量路由 個人部落格、中小型網站、希望快速完成 HTTPS、CDN 與基本資安

如果你的架構已經大量使用 S3、CloudFront、ALB、API Gateway、ECS，把 DNS 與防護留在 AWS 會比較一致，也能透過 Terraform 或 CloudFormation 一起管理。

但如果跟筆者一樣，只想替一般網站快速補齊 DNS、SSL、CDN 與基礎 WAF，Cloudflare 的整合度真的很香，Free 方案通常就夠用了。

AWS 的產品與計費會調整，實際採用前可以再查看 Route 53 官方文件、CloudFront 官方文件 與 AWS WAF 官方文件。

事前準備與注意事項

開始前需要準備：

  • 一個 Cloudflare 帳號
  • 一個已在 GoDaddy 購買的網域
  • 目前網站主機的 IP 或服務提供的 CNAME
  • 如果有使用 Email，要先記錄 MX、TXT、DKIM、SPF、DMARC 等 Record

這邊最重要的不是手速，而是先把舊 DNS 確認清楚。

更換 Nameserver 之後，網路上的人會改問 Cloudflare：「這個網域要去哪裡？」如果 Cloudflare 漏掉網站、信箱或驗證用 Record，就可能出現網站正常但信箱壞掉，或者反過來的奇妙場面。

強烈建議先將 GoDaddy 現有 DNS Record 截圖或匯出，尤其有使用 Google Workspace、Microsoft 365 或其他企業信箱的人。

確認 DNS 與 Proxy 狀態

回到 Cloudflare，等待 Overview 顯示網域為 Active，代表 Nameserver 已經切換成功。

接著到：

Cloudflare 的 Record 旁邊會看到雲朵：

  • Proxied（橘色雲朵）：流量先經過 Cloudflare，才能使用 CDN、WAF、DDoS 防護與 Edge SSL
  • DNS only（灰色雲朵）：Cloudflare 只回答 DNS，流量直接前往原始主機

一般網站的 A、AAAA、CNAME 可以視需求開啟 Proxied；MX 與郵件相關紀錄則維持 DNS only。不是所有連線都能直接套一朵橘色雲上去，亂開可能讓 Email 或非 HTTP 服務無法使用。

開啟橘色雲朵後，請求到底怎麼走？

當使用者在 Browser 輸入 https://example.com，整個流程大致如下：

  1. Browser 查詢 DNS：瀏覽器先詢問 example.com 對應的 IP。
  2. Cloudflare DNS 回傳 Edge IP：因為 Record 已開啟 Proxied，DNS 不會直接暴露 Origin Server IP，而是回傳 Cloudflare Anycast IP。
  3. Request 先進 Cloudflare Proxy：TLS 連線會先到 Cloudflare Edge。
  4. 套用 SSL、WAF 與 CDN：Cloudflare 會先處理 HTTPS、檢查 WAF 規則，並判斷 Cache 是否已有可直接回傳的內容。
  5. 需要時才前往 Origin Server：Cache Miss 或動態請求才會由 Cloudflare 繼續送到後面的 VM、VPS、GitHub Pages 或其他 Origin。
  6. Response 原路返回：Origin 回應先回到 Cloudflare，Cloudflare 視規則快取或加工後，再把結果傳回 Browser。

所以橘色雲朵並不是單純換一個 DNS 而已，它讓 Cloudflare 真正站到訪客與主機中間。WAF 之所以能在惡意請求抵達機器前擋掉它，也是因為流量有先經過這層 Proxy。

這時 Cloudflare 只負責回答 DNS，不會替這段 Web 流量套用 WAF、CDN、Edge SSL 或 HTTP Analytics。

方法一：使用 192.0.2.1 搭配 Redirect Rule

這個方法最簡單，不需要修改 GitHub Repository 的 Pages 設定。

這個方法要注意一件事情：

Cloudflare WAF 只能檢查進入 example.com、準備取得 301 回應的那一次請求。瀏覽器跳到 rexhung0302.github.io 之後，網址與流量都已經離開你的 Cloudflare Zone，所以你在 example.com 設定的 WAF、Cache Rule、Analytics 都無法繼續套用。

GitHub 本身當然仍有自己的平台防護，但那已經不是你在 Cloudflare 設定的這套 WAF。另一個缺點是訪客最後會在網址列看到 rexhung0302.github.io，自己的網域不會保留下來。

如果只是把舊網址轉到新網址，這個方法很方便；如果希望網址列始終顯示自己的網域，請使用下一種方式。

每個 GitHub 帳號產生的 Hostname 與驗證碼都不同，請直接複製自己畫面上的內容，不要照抄別人的文章，也不要把完整 TXT Value 公開。

回 GitHub 按下 Verify 後，可能不會立刻成功。DNS 還在傳播時會看到 Unverified 或警告訊息，可以稍等一段時間再驗證，不需要一直刪除重建。

SSL 不用另外申請，但還是要設定

這一段直接先說結論：不用再另外申請 SSL 憑證。

Cloudflare 完整託管網域後，會自動替根網域與第一層子網域簽發免費的 Universal SSL，並自動處理續約。可以到以下位置確認憑證狀態：

看到 Universal Certificate 為 Active 就完成了。剛切換 Nameserver 時，憑證可能還在 Pending，等一段時間再回來看即可。

不過 SSL 其實有兩段：

Universal SSL 保護的是前半段；後半段仍取決於原始主機有沒有憑證，所以到 SSL/TLS → Overview 時要正確選擇 Encryption mode。

Mode Cloudflare 到 Origin 建議
Flexible HTTP 只適合暫時救急，可能產生 Redirect Loop，不建議長期使用
Full HTTPS，但不驗證 Origin 憑證是否合法 比 Flexible 好，但仍可能連到錯誤或偽造憑證
Full (strict) HTTPS，並驗證有效且 Hostname 正確的憑證 正式環境推薦

如果主機端已經有 Let’s Encrypt 或其他 CA 簽發的有效憑證，直接使用 Full (strict)。如果沒有，也可以在 Cloudflare 建立 Origin CA Certificate 安裝到主機；不過它只供 Cloudflare 與 Origin 之間使用，不能拿來讓瀏覽器直接信任。

最後到：

把 Always Use HTTPS 打開，讓所有 http:// 請求自動轉到 https://。如果頁面仍出現 Mixed Content，再檢查網站內是否寫死 http:// 圖片或 Script，必要時也可以開啟 Automatic HTTPS Rewrites。

Cloudflare 官方文件： Edge certificates、Always Use HTTPS。

設定 Cloudflare WAF

WAF 全名是 Web Application Firewall，它不是取代主機防火牆，而是在 HTTP 請求抵達網站前，依規則攔截 SQL Injection、XSS、惡意 Bot 或異常流量。

Bot 與 DDoS

Cloudflare 的 L3/L4 與 L7 DDoS Protection 會自動運作，不需要另外打開。Free 方案還能到 Security → Settings 開啟 Bot Fight Mode，針對已知自動化 Bot 進行 Challenge。

但 Bot Fight Mode 無法針對個別路徑設定例外；如果網站有 GitHub Webhook、金流 Callback、Uptime Monitor 或其他合法機器流量，開啟後記得實際測試。

驗證與常見問題

檢查 HTTPS

第一個請求應該回傳 301 或 308 並導向 HTTPS；第二個則應正常取得網站回應。

檢查是否經過 Cloudflare

回應 Header 通常可以看到 server: cloudflare、cf-ray 等資訊。如果完全看不到，先檢查該 DNS Record 是否為橘色雲朵。

網站出現 Too Many Redirects

常見原因是 Origin 已強制 HTTPS，但 Cloudflare 使用 Flexible，兩邊互相轉址到天荒地老。主機有有效憑證時直接改成 Full (strict)。

出現 525 或 526

  • 525：Cloudflare 與 Origin 的 TLS Handshake 失敗
  • 526：Full (strict) 無法驗證 Origin 憑證

檢查主機端憑證是否過期、Hostname 是否正確、443 Port 是否開放，以及防火牆有沒有擋住 Cloudflare IP。

Email 突然收不到

檢查 MX、SPF、DKIM、DMARC 是否完整搬到 Cloudflare，郵件主機的 Record 也不要錯誤開啟 Proxy。

WAF 擋到正常使用者

到 Security → Events 查看觸發的 Service、Rule ID、Action 與請求資訊，再針對確定安全的條件建立 Skip 或調整規則。不要只因為一次誤判就把整個 WAF 關掉。

總結

最終成果

完成 DNS、SSL、WAF 與 GitHub Pages Custom Domain 後，網站已經能透過自己的網域正常開啟；上圖則是 Cloudflare 針對高風險請求顯示的實際安全驗證畫面。

整個流程其實可以濃縮成：

Cloudflare 最大的優勢不是某一項功能特別神奇，而是把 DNS、Proxy、CDN、SSL、DDoS 與基礎 WAF 放在一起。對個人部落格或中小型網站來說，不用分別串好幾個服務，就能先得到一套堪用的安全與效能基礎。

當然，開啟 Cloudflare 並不代表網站從此刀槍不入。程式漏洞、套件更新、主機權限、備份與密碼管理還是要自己負責；WAF 是多一層防線，不是無敵星星。

最後提醒一次：更換 Nameserver 前先備份 DNS，完成後一定要測試網站、HTTPS、Email 與第三方 Callback。 這幾個步驟都有確認，基本上就可以安心收工了！
